SimpliFreeze Azure Deployment Guide

Overview

SimpliFreeze is a lightweight, Docker-based application that helps IBM Cognos Analytics administrators discover, organize, and manage schedules across Cognos environments. SimpliFreeze provides schedule discovery, inventory management, tagging, export and import capabilities, and licensed freeze and thaw operations while preserving original schedule state.

Prerequisites

IBM Cognos Analytics

SimpliFreeze requires IBM Cognos Analytics 12.2.0 or later. Earlier versions are not supported because required REST API endpoints are unavailable.

Azure Requirements

  • An active Azure subscription.
  • Permission to create virtual machines, networking resources, and public IP addresses.

User Requirements

  • Cognos REST API URL.
  • Cognos API key.
  • Ability to configure firewall rules if Cognos is hosted on-premise or behind a VPN.

Deployment Steps in Azure Portal

1. Start the Deployment

Open the Azure Marketplace listing for SimpliFreeze, select your desired plan (Trial, Standard, or Enterprise), and click Create.

2. Basics

Configure the foundational Azure resource settings for your virtual machine:

  • Subscription: Select the active Azure subscription where billing and resource ownership will be managed.
  • Resource Group: Choose an existing resource group or create a new dedicated one (e.g., rg-simplifreeze-prod) to keep all deployment assets grouped logically.
  • Region: Select the Azure region closest to your users or your hosted IBM Cognos Analytics environment to minimize network latency. Note: Depending on your subscription context or pre-selected scope, this prompt may be pre-populated or omitted automatically by the portal.
  • Virtual Machine Name: Enter a unique identifier for the virtual machine resource (defaults to simplifreezevm).
  • Admin Username: Enter the administrative username for logging into the virtual machine (avoid generic names like root or admin).
  • Admin SSH Public Key: Paste your SSH RSA public key string (starting with ssh-rsa) for secure Linux authentication. If you need to generate a new key pair, open PowerShell and run: ssh-keygen -t rsa -b 4096 -f "$env:USERPROFILE\.ssh\id_rsa" (the public key will be saved to $env:USERPROFILE\.ssh\id_rsa.pub).
  • Application Name: Specify a name for the managed application (ie. simplifreeze-app).
  • Managed Application Resource Group: Specify or accept the managed resource group name where Azure will automatically provision and isolate the underlying solution resources and stock networking components.

3. SimpliFreeze Configuration

Configure initial application credentials and network access parameters:

  • SimpliFreeze Admin Username: Set the primary administrator username for logging into the SimpliFreeze web application.
  • SimpliFreeze Admin Email: Specify the contact email address for the SimpliFreeze administrator.
  • SimpliFreeze Admin Password: Set a secure password for the primary administrator account (minimum 12 characters).
  • Additional Allowed Hostnames / Load Balancer FQDN: Optional. Enter comma-separated external hostnames or domain names permitted to access the application. The VM name is included automatically.
  • Cognos Allowed Hosts: Enter the hostnames or IP addresses of your IBM Cognos servers (comma-separated).

4. TLS Certificates

SimpliFreeze secures all web traffic using HTTPS. You must choose how application and CA certificates are provisioned during deployment:

Organization-Provided Certificates (Recommended for Production)

If your enterprise uses internally signed or enterprise CA certificates, upload the corresponding PEM-encoded files:

  • TLS Certificate (server.crt): Upload your PEM/CRT public certificate or certificate chain file.
  • TLS Private Key (server.key): Upload your PEM private key file.
  • Cognos CA Certificate (cognos.pem): Optional. Upload the PEM CA certificate required to verify connections to your Cognos server over SSL/TLS.

SimpliFreeze automatically mounts these credentials into /opt/simplifreeze/deploy/certs/ for the NGINX reverse proxy container to ensure secure, trusted connections.

Automatically Generated Self-Signed Certificate (Default)

If you leave the certificate upload fields blank, SimpliFreeze automatically generates a secure self-signed certificate upon first boot. While fully encrypted, your browser will display an initial security warning until you trust the certificate locally or replace it later. If a public IP address is configured, it is automatically injected as a Subject Alternative Name (SAN).

5. Networking & Public IP

Configure networking settings for your deployment:

  • Managed Network: SimpliFreeze automatically deploys using a stock network configuration within the managed resource group, streamlining setup without requiring custom virtual network or subnet provisioning.
  • Public IP Address: Select New to create a dynamic or static public IP, or select None to keep the virtual machine entirely private within your network.
  • DNS Name Label Prefix: If you choose to enable a public IP address, enter a unique prefix to establish an Azure-managed fully qualified domain name (FQDN), such as <prefix>.<region>.cloudapp.azure.com.

6. Review + Create

Azure runs a final automated validation check against your parameter inputs. Once validation passes, click Create to provision the infrastructure and trigger the automated installation script.

Post-Deployment Steps

Accessing & Network Configuration

SimpliFreeze enforces an allowed-hosts list for security. During deployment, the VM's hostname and any provisioned public IP address are automatically added to ALLOWED_HOSTS.

1. Inbound Access (Reaching SimpliFreeze)

To reach the SimpliFreeze interface, inbound traffic on Port 443 (HTTPS) or Port 80 (HTTP) must be permitted:

  • Public Access: If deployed with a Public IP, ports 80 and 443 are automatically opened in the Network Security Group during deployment. You can access SimpliFreeze immediately using your configured DNS label or public FQDN, for example: 
    https://simplifreeze-prod.eastus.cloudapp.azure.com/simplifreeze/
  • Private / VNet-Peered Access: If deployed without a Public IP to keep SimpliFreeze completely isolated within your network, ensure your internal Network Security Groups allow inbound web traffic on ports 80/443, and configure access via:
    • VNet Peering: Connect your internal corporate or application Virtual Network to simplifreeze-vnet to route traffic over Azure’s private backbone.
    • Private DNS: Add an entry in your Azure Private DNS Zone or corporate DNS server pointing your internal hostname to the VM's private IP.
    • Certificates: Ensure your TLS certificate covers your internal domain name or private IP to avoid browser security warnings.

2. Outbound Access (Connecting to Cognos)

Regardless of whether SimpliFreeze is deployed with a Public or Private IP, it must establish outbound connections to your Cognos Analytics environment to discover and manage schedules.

Ensure your Network Security Groups (NSGs) and corporate firewalls allow outbound traffic from the SimpliFreeze VM to your Cognos server:

  • Port 9300: Standard for direct communication with the Cognos Dispatcher / Content Manager.
  • Port 443 / 80: If traffic is routed through an internal web gateway, IIS, or reverse proxy.

Administrative SSH Access

Direct SSH access is completely optional and disabled by default. If your team requires SSH access, you must first open Port 22 via an inbound Network Security Group (NSG) rule or connect through an Azure Bastion / private VPN.

Once network access is established, authenticate using the RSA key created during deployment: 

ssh <admin-user>@<hostname-or-private-ip>

Note: If you generated your key using the default path ($env:USERPROFILE\.ssh\id_rsa), your SSH client will use it automatically without requiring additional flags.

Docker containers are located under:

/opt/simplifreeze/

Connecting to Cognos

All Cognos configuration is performed inside the SimpliFreeze UI.

On the Settings page, enter:

  • Cognos REST API URL
  • API Key

Click Test to verify connectivity.

Updating SimpliFreeze

To update SimpliFreeze:

docker compose pull
docker compose up -d

Troubleshooting

This section provides practical guidance for diagnosing and resolving common issues encountered during deployment or operation in Azure. Each item includes likely causes, recommended fixes, and steps for reviewing logs inside the SimpliFreeze VM.

Invalid Certificate Errors

Common Causes:

  • The Cognos CA certificate is missing or not in PEM format.
  • The Cognos CA certificate path in .env is incorrect.
  • Hostname verification is enabled but the Cognos certificate CN/SAN does not match.
  • The VM's HTTPS certificate (self-signed or organization-issued) is unreadable by the container.

Fixes:

  • Verify the Cognos CA certificate exists on the VM and is valid PEM.
  • Confirm the corresponding path in .env points to the correct file.
  • For Testing / Self-Signed Certs: Disable hostname verification in your .env configuration if self-signed defaults trigger a mismatch.
  • For Production: Ensure the Cognos server certificate's CN or SAN strictly matches the hostname used in the SimpliFreeze Settings page.
  • Check file permissions for the installed certificate and key inside the VM.

Connection Failures to Cognos

Common Causes:

  • Cognos is not reachable from the Azure VM.
  • Firewall rules or network ACLs block outbound traffic.
  • Incorrect Cognos hostname or port in the Settings page.
  • COGNOS_ALLOW_HTTP=false in .env while Cognos is only serving HTTP.

Fixes:

  • From the VM, test reachability using curl -v https://your-cognos-host or curl -v http://your-cognos-host.
  • Verify that outbound traffic from the VM to Cognos is allowed by your network team.
  • Update the Cognos REST API URL in the Settings page to match the actual hostname and port.
  • If Cognos is only available over HTTP and your organization accepts that risk, set COGNOS_ALLOW_HTTP=true in .env and restart the stack.

Authentication Issues

Common Causes:

  • The Cognos API key was copied incorrectly (extra spaces, hidden characters).
  • The API key has expired.
  • The API key has been locked in Cognos.
  • The API key was deleted or regenerated but not updated in SimpliFreeze.
  • The Cognos user associated with the API key lacks permission to access schedules.
  • The Cognos user account is disabled or suspended.

Fixes:

  • Open Cognos Analytics → Manage → Accounts → (User) → API Keys and verify the key is active, not expired, not locked, and not deleted.
  • Re-copy the API key carefully and paste it into the SimpliFreeze Settings page.
  • If the key is locked or expired, generate a new API key.
  • Ensure the Cognos user has sufficient permissions to view and manage schedules within the target Cognos environment.
  • If the user account is disabled, re-enable it or create a new API key.
Important: If an API key is locked, expired, or deleted in Cognos Analytics, it cannot be recovered. A new key must be generated and updated in the SimpliFreeze Settings page.

Slow or Incomplete Schedule Discovery

Common Causes:

  • Large Cognos environments containing thousands of schedules.
  • Network latency between Azure and Cognos.
  • Slow Cognos REST API responses.
  • High utilization on the Cognos Content Manager.
  • The configured schedule retrieval limit has been reached.

Fixes:

  • Verify network connectivity between Azure and Cognos.
  • Review Cognos server health and Content Manager performance.
  • Perform schedule refreshes during lower utilization periods.
  • Review the configured schedule retrieval limit.

SimpliFreeze retrieves schedules using the SIMPLIFREEZE_SCHEDULE_LIMIT environment variable.

If the number of available Cognos schedules exceeds this limit, SimpliFreeze may not retrieve every schedule during discovery. When the configured limit is reached, SimpliFreeze displays a warning indicating that additional schedules may exist.

To increase the retrieval limit, edit: 

/opt/simplifreeze/.env

Then update: 

SIMPLIFREEZE_SCHEDULE_LIMIT=10000

After modifying the value, restart the application: 

docker compose up -d

Container Startup Errors

Common Causes:

  • Uploaded certificates are invalid or not in a supported format.
  • PostgreSQL container failed to initialize due to invalid credentials or disk issues.
  • Volume permissions preventing PostgreSQL from writing data.

Fixes:

  • Verify that uploaded certificates are valid PEM files and were accepted during deployment.
  • Ensure database credentials in .env have not been modified after deployment.
  • Check filesystem permissions and confirm the VM's OS disk is healthy and writable.

Important File Locations

The SimpliFreeze VM stores all configuration files, certificates, and Docker resources under a single directory. These files are useful when troubleshooting, enabling DEBUG logging, or verifying certificate installation.

  • Application Directory:
    /opt/simplifreeze/
    Contains the Docker Compose stack, environment file, certificates, and support scripts.
  • Environment File:
    /opt/simplifreeze/.env
    Stores runtime configuration values, including Cognos connectivity settings, allowed hosts, schedule retrieval limits, licensing configuration, and logging settings.
  • Certificates:
    /opt/simplifreeze/deploy/certs/
    Contains the HTTPS certificate and key used by NGINX, as well as any Cognos CA certificate uploaded during deployment.
  • Docker Compose File:
    /opt/simplifreeze/docker-compose.yml
    Defines the SimpliFreeze services (web, nginx, db) and their configuration.
  • Log Files (via Docker): 
    docker compose logs -f web
docker compose logs -f nginx
docker compose logs -f db
    Logs are streamed from containers rather than stored as files.

These locations are consistent across all Azure plans and do not change when resizing the VM or updating SimpliFreeze.

Recommended Diagnostic Workflow:

  1. Start with docker compose logs -f simplifreeze-web-1 to identify application-level errors.
  2. Check docker compose logs -f simplifreeze-nginx-1 for certificate or routing issues.
  3. Review docker compose logs -f simplifreeze-db-1 for database initialization or storage issues.
  4. Temporarily set LOG_LEVEL=DEBUG in .env for deeper insight into Cognos REST interactions, then run docker compose up -d to apply changes.
Note: Always return LOG_LEVEL to INFO after troubleshooting to avoid excessive log output.
